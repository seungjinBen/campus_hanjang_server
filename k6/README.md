# k6 부하 테스트

N+1 쿼리 개선 전후 응답 시간을 비교하기 위한 부하 테스트 스크립트와 측정 결과.

## 파일

| 파일 | 용도 |
|---|---|
| `load-test.js` | 메인 시나리오 — 카드 조회 / 선택 / 쪽지 수신함. 50 → 500 → 1000 VU 단계 스파이크 |
| `perf-test.js` | 100 / 500 VU 동시 접속 기준선 측정 (HikariCP 풀 임계점 확인) |
| `seed-data.sql` | 테스트 유저 1,000명 + 당일 카드 5,000장 시드 (멱등) |
| `run-tests.sh` | `baseline` / `optimized` / `compare` 실행 래퍼 |

결과 원본(`results/*.json`, 수십 MB)은 커밋하지 않고 아래 요약만 기록한다.

## 실행

```bash
psql -U <user> -d campus -f k6/seed-data.sql
./gradlew bootRun --args='--spring.profiles.active=dev'
k6 run k6/load-test.js --summary-export=k6/results/optimized-summary.json
```

dev 프로파일의 `/api/dev/test-tokens`로 테스트 토큰을 발급받으므로 prod에서는 실행되지 않는다.

## 측정 결과 (2025-05-25, 로컬 dev 서버, `load-test.js`)

단계: 50 VU 30s → 500 VU 60s → 1,000 VU 30s → 0 VU 30s. 50 VU가 실제 운영 피크 수준이며 1,000 VU는 20배 스파이크다.

| 지표 | N+1 개선 전 | 개선 후 | 변화 |
|---|---|---|---|
| 총 요청 수 | 10,670 | 21,431 | 2.0× |
| 처리량 (req/s) | 62.3 | 128.0 | 2.1× |
| 전체 p50 | 3,489 ms | 2,104 ms | −40% |
| 전체 p95 | 21,870 ms | 8,810 ms | −60% |
| 전체 p99 | 26,047 ms | 10,296 ms | −60% |
| 카드 조회 p95 | 23,527 ms | 8,873 ms | −62% |
| 선택 p95 | 21,326 ms | 9,080 ms | −57% |
| 쪽지 수신함 p95 | 21,190 ms | 8,540 ms | −60% |
| 5xx 응답 | 59 | 0 | — |
| 체크 실패 | 0 / 12,177 | 0 / 24,461 | — |

쿼리 수 변화: 카드 10장 조회 22 → 4 쿼리, 쪽지 N건 조회 2N+1 → 3 쿼리 (`@EntityGraph` + 배치 조회).

주의할 점:

- 스크립트의 p95 임계값(카드 2,000 ms 등)은 1,000 VU 스파이크 구간을 포함한 집계라 두 실행 모두 미달이다. 임계값은 목표치이지 달성치가 아니다.
- `http_req_failed`에는 하루 선택 한도 초과(400)와 rate limit(429)이 포함된다. 정상 비즈니스 응답이라 `error_rate` 커스텀 지표에서는 제외했다.
- 로컬 단일 머신(서버 + k6 동일 호스트) 측정값이다. 운영 환경 절대값이 아니라 개선 전후 상대 비교 용도다.
- 운영 중 실측 피크 동시접속 값은 별도 모니터링 데이터 기준으로 기재 예정.
